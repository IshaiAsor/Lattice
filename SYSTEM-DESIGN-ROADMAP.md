`server-ci.yml`, VSCode debug configs/workspace entry). Its 3 remaining pieces were ported first:
Google OAuth account-linking (`/api/google/auth`, `/auth/login`, `/token`) was already fully

overlays** repointed `/api` → `api` service and `/api/google` → `google-home` (prod didn't have

`api-prod`-ready; prod `api-prod` promotion stays manual, matching every other `*-prod` stage).

`lattice-server` dropped from the `lattice-app` Warehouse subscription. Backoffice repointed off
`environment.apiUrl` entirely (removed the field); 2 dead methods (`addDevice`,
`updateDeviceStatus`) and 2 unused fields deleted along the way. Gitops changes were pushed to

`lattice-ingress`/`lattice-tls` on 2026-07-05.

## F10 — Blueprints

> **Redesigned 2026-07-20 → [docs/plans/blueprints-redesign.md](docs/plans/blueprints-redesign.md).**
> The 2026-07-10 design was built, disliked, and shelved (`wip/blueprints-and-ai-rulegen-shelved-2026-07-13`;
> post-mortem [docs/plans/blueprints.md](docs/plans/blueprints.md)). It is **not** being revived —
> the redesign supersedes it. Key differences resolved with the user:
>
> - **Slots bind through sealed templates**, not `capability_key`/device-pin dual mode. A slot
>   points at a released `SealedTemplate`; derive reuses its version-range match + `materializeForUserDevice`.
>   No `DEVICE_ROLE_STR`, no `devices.role_tag`, no firmware change. Non-sealed slots are out of scope.
> - **Reconcile, not snapshot re-derive.** A blueprint is desired state; releasing a new version
>   flows structural changes into live instances (create/update/disable, never delete), skipping any
>   user-edited entity (`user_modified`) and never touching user overrides.
> - **Parameterize, don't mutate.** Derived automations store `@param.x`/`@phase.x` references
>   resolved at evaluation time (precedence: user override → current phase → blueprint default), via
>   a shared `packages/params` used by automation-worker, api validation, and ml-router (pipeline
>   prompts + sensor ranges). Phase advance = one column write; reconcile/phase/user-edit write
>   disjoint places and cannot clobber each other.
> - **Areas are a standalone primitive.** "These devices belong together" is a user-createable
>   `Area`, not welded to derivation. Grouped notifications + dashboard sectioning + AI scope key
>   off it. A derive creates one. Ships first, independently.
> - **Phases auto-advance** on elapsed duration (rides automation-worker's 10s cron).
>
> Generic naming holds: domain-specific blueprints are runtime admin content only — never repo
> seeds/code/tests. Build order below matches the redesign doc §13; the builder UI is deliberately last.

## F23 — State reconciliation (periodic read-back of command state)

**The problem: `current_state` for a command action is not an observation, it is a cache of the
last ack the platform happened to see.** `user_device_actions.current_state` has exactly two
writers, both funnelling into `writeScalarState` (`digest-service/src/state-write.ts`): the
telemetry consumer, and the action-result consumer. Telemetry (read-surface) actions therefore
self-correct — a cyclic reading overwrites whatever the DB believed. **Command actions have no
such loop**: `action-result.consumer.ts` is, by its own comment, "the ONLY path that writes
current_state for command actions", so the row only ever changes when an ack arrives. If an ack
is never seen, the DB keeps the stale value indefinitely and nothing ever notices.

**Ways it goes wrong, all of them real:** an ack lost in transit (broker drop, digest down, a
DLQ'd message, or the RabbitMQ consumer-death failure mode already recorded in this repo); a
device rebooting and restoring NVS state while the ack consumer is down, so the unsolicited
boot-restore ack (`BaseCommandAction::loadState`) is dropped; a timed hold releasing itself
on-device (`DurationState` auto-off) with the release ack lost; and any change made to the
actuator outside the platform. `device_commands` rows that stay `sent` are the population where
this is most likely — the schema comment already reads them as "sent, unconfirmed" — and today
nothing ever follows up on one.

**Why it matters:** `current_state` is not display-only. `rules.engine.ts` gates `device_status`
and threshold conditions on it, `ml-router`'s enrich stage puts it in the LLM prompt, and
`google-home/device.actions.service.ts` reports it verbatim to Google QUERY. A wrong value
propagates silently into automation decisions and to Google, and the platform has no way to
distinguish "the pump is off" from "we last heard it was off".

**The mechanism already exists on both ends of the wire — nobody uses it.** Firmware reserves
the `read` verb (`MqttActionsHandlerService.h:111-145`): on a command-only action it replies on
the ack topic with the NVS-persisted state via `getState()`, never executing and never reaching
the parity-critical `validateActionPayload`. The simulator mirrors it
(`tools/device-sim/lib/sim-device.js:467`), so parity already holds. But **no backend service
ever sends it** — a grep for the verb across `services/` returns nothing. So this group is
platform-side only: no firmware change, no sim change, no new MQTT contract.

**Design calls to hold to:**

- **The device wins.** A read-back is an observation, not a command: on divergence the DB is
  corrected to what the device reports, never the reverse. Re-asserting the intended state onto
  the device is deliberately **out of scope** — "which desired state" is a policy question, and
  silently actuating a valve because an ack went missing is worse than the stale row.
- **A read is not a command.** It has no `target_state`, so it must not create a `device_commands`
  dispatch row. Watch `recordAck`'s no-open-row branch: as written it would create a fresh
  `source: 'device'` history row for _every_ read ack, fabricating a command history entry per
  sweep per action.
- **A reconcile ack must not be filtered as a stale echo.** The UI treats a `commandId` it did
  not issue as not-latest (`isLatest` in `group-bottom-sheet.component.ts:52`), so digest should
  correlate the read internally but emit the socket update _without_ a commandId — i.e. as the
  authoritative refresh it is.

- Pipeline-worker has **4 consumers**: trigger (creates PipelineRun, publishes first stage), sensor_digest, command_exec, finalization (`q.pipeline.stage.done` → update run, publish `pipeline.result`, socket emit).
- **ml-router is a queue consumer, not an HTTP service**: `setupModelQueues()` asserts one queue per registered ML model at startup (`q.pipeline.stage.{kind}.{name}.{version}`), prefetch 1 for LLM / 4 for VLM.
- `advancePipeline()` helper (~45 lines, inlined in both pipeline-worker and ml-router): writes PipelineRunStage, then publishes next stage's queue or `pipeline.stage.done` (status completed/failed). Errors → done with `failed` → message lands in DLQ.
- Why: LLM inference can take 60+ s — HTTP blocks, no retry; per-stage queues give independent backpressure, DLQ, and per-model scaling.

**3. SensorBlueprint** (new Prisma model): `sensor_groups` JSON (named capability groups), `profile` JSON (target ranges), optional `camera_device_id`; `Pipeline.blueprint_id` FK.

- Validation **hard at pipeline creation**, trusted at runtime: any vlm/llm stage → blueprint required; any vlm stage → blueprint must have `camera_device_id`.
- `sensor_digest` stage reads groupings/profile from the blueprint (not from flat stage config); VLM/LLM handlers read the cached camera frame via the blueprint's camera device.
- Stage chains: `vlm → sensor_digest → llm → command_exec` (with camera) or `sensor_digest → llm → command_exec` (sensors only).

⚠️ The plan's JSON examples use farming terms (`plant_type`, `nutrients`…) — predates the generic-naming rule. When implementing, all examples/seeds must be domain-agnostic.

**Where it lands in the roadmap:** F1.4 builds `packages/queue` with the static RKs/DLQ_ARGS/payload types from day one (no migration later) · F6 workers consume them · F8.1 adds SensorBlueprint + validation · F8.2 the 4 consumers + advancePipeline · F8.3 ml-router model queues.
