## 1. Why

Three separate problems land on the same missing piece.

**Acceptance mutates the environment prod is promoted from.** `docs/TESTING.md` puts acceptance
against staging, as the `e2e-bot` user, with hard rules to contain the damage — "never real user
data", "every suite cleans up what it creates", MACs prefixed `SIM-E2E-` "so leaked residue is
identifiable and sweepable". That last phrase is the tell: the rules exist because the environment
cannot absorb a mistake. Staging today holds **exactly one user account**, so there is no `e2e-bot`
at all and any mutating run would touch the only real one.

**Four review rows cannot be tested anywhere.** Staging has 0 released sealed templates (F3.18 has
nothing to preview), no path to a fresh provision (F5.11), and no mail catcher — `SMTP_HOST` comes
from the sealed `notification-secret`, so F15.8/F15.9 would send real mail through a real provider.
Locally, the ephemeral test stack collides with the dev stack on every app port (3100, 3004–3011);
only infra is offset (15432, 16379, 25672).

**Nothing verifies any promotion.** All 28 Kargo stages carry only `promotionTemplate.steps`
(git-clone → kustomize-set-image → git-commit → git-push). There is no `spec.verification`, no
AnalysisTemplate, no sanity Job anywhere in `oci-k3s-gitops` — despite `docs/TESTING.md` describing
the Kargo sanity gate as though it exists. **That gate was never built.**

## 2. What it is

A `lattice-e2e` namespace holding a full app stack with its own data plane:

- every service, its own `postgres` / `rabbitmq` / `emqx` / `valkey`
- **`mailpit` in-namespace**, with `SMTP_HOST=mailpit` — no mail can escape the cluster
- its own seed: an `e2e-bot` user, a released sealed template, a camera device
- `lattice-iot-e2e.duckdns.org` for HTTP, MQTTS by SNI on the shared 8883

## 3. Capacity — measured, not assumed

|        | node `k3s-a1-1`                                    |
| ------ | -------------------------------------------------- |
| CPU    | 455m actual (**11%**) · 2565m requested (64% of 4) |
| Memory | 8.5 GB of 24 GB (**35%**) · requests 19%           |
| Disk   | **50.5 GB of 192.7 GB (26%)** · no DiskPressure    |

The whole 18-pod `lattice-stg` stack requests **950m CPU / 1600Mi memory**. A second copy is about
+24% CPU requests and +7% memory — comfortable. (Earlier notes claiming 80% CPU and zero disk
headroom predate the 200 GiB volume and the node reshape; they were wrong.)

MQTTS needs no new port. 8883 is already routed by SNI, so an e2e broker claims its own hostname:

```
HostSNI(`lattice-iot-stg.duckdns.org`)   → emqx:8883      # staging, today
HostSNI(`mqtt.lattice-local.duckdns.org`) → frps          # local tunnel, today
HostSNI(`lattice-iot-e2e.duckdns.org`)   → emqx:8883      # proposed
```

## 4. Design decisions

1. **Never in the prod promotion path.** The e2e stage may track images, but a broken e2e
   environment must not gate, block or delay a prod promotion. Wired deliberately, not copied from
   a staging stage.
2. **ArgoCD app on manual sync.** Auto-sync with prune + self-heal would revert any image patched in
   by a local deploy (Phase 2). Manual sync is what makes one-click-from-local possible at all.
3. **Mailpit in-namespace, not a provider.** This is the whole reason F15.8/F15.9 become testable:
   real SMTP path, zero real mail.
4. **Its own sealed-secrets variant**, generated by the same `seal_secrets.ps1` path as the others.
5. **Reset is a first-class operation.** The value is a _clean_ environment: either a Job that drops
   and reseeds, or a documented `delete ns` → resync. Without this it rots into a second staging.

## 5. Phases

**Phase 1 — the environment.** Overlay, ArgoCD app (manual sync), DuckDNS host, SNI route, mailpit,
seed job. _Unblocks F3.18, F5.11, F15.8, F15.9 immediately — the four rows that are stuck today._

**Phase 2 — one-click from local.** A `deploy-e2e` script: build changed services, push under an
`-e2e` tag, patch the deployments. Needs a `device-sim` image (Dockerfile exists at
`tools/device-sim/Dockerfile`, but no workflow builds it) if the simulator runs in-cluster.

**Phase 3 — make the suite green.** _Hard prerequisite for any gate._ A suite that is never green
can only produce a permanently blocked pipeline or an allowlist that rots.

**Phase 4 — bundled freight.** 14 warehouses × 2 stages means an e2e gate has no natural home today:
either the suite runs 14 times per release, or one service's stage arbitrarily carries it. One gate
wants one freight — the redesign already noted as planned.

**Phase 5 — the gate.** e2e stage with `spec.verification`; staging takes freight from e2e rather
than direct from the warehouse. **Note this makes e2e always-on infrastructure**, not the on-demand
environment of Phase 1.

> **Cheap intermediate win:** since nothing is verified today, wiring the verification mechanism
> with `test:sanity` first — read-only, fast, already written, already documented as existing — is a
> fraction of the work and makes every promotion safer immediately. Prove the mechanism with the
> green suite; swap e2e in once it deserves to hold the door.

## 6. Open questions

- **Always-on or on-demand?** Phase 1 wants on-demand (costs nothing at rest). Phase 5 forces
  always-on. Decide before Phase 1 is committed, since it changes the ArgoCD sync policy.
- **Where does the device come from for F5.11?** A sim pod needs an image and a build. A real board
  pointed at the e2e broker needs certs.
- **Alerting blast radius.** A third stack will page the existing Alertmanager routes unless
  explicitly excluded.
