# F25.7 — EMQX device credentials and topic ACLs

**Status:** replanned 2026-10-26 (first plan 2026-09-17, never started); D1 = token fingerprint
in Postgres, decided 2026-10-26; Phase 0 awaiting go-ahead · **Covers:** F25.7 ·
**Feeds:** F25.8 (mTLS)

**Roadmap test:** _a device credential is refused publish and subscribe outside its own topic prefix._

**Headline:** anyone on the internet can control any device on the platform. Signup is open
(Google sign-in or `/api/auth/register`). The backoffice session token that signup hands out is
signed with `JWT_SECRET`. EMQX accepts **any** token signed with `JWT_SECRET` as an MQTT
credential, and never checks that the token belongs to the `username`/`clientid` sent in
CONNECT. So: sign up, copy `access_token` from `localStorage`, connect to
`device.<host>:8883` as `username=<any user id>`, `clientid=<any device id>`, and read that
device's commands or publish its telemetry, acks and status. Both ids are sequential integers.

The 2026-09-17 plan framed this as "a stolen token". That was too mild. No theft is needed,
only a free account.

**What changed in this replan:**

1. **Containment first (Phase 0).** One broker setting, `verify_claims = {purpose = device_usage}`,
   closes the zero-effort path within a day. It needs no new code and no firmware change, and it
   is safe for the existing fleet (§4).
2. **The structural fix changed (decided 2026-10-26).** The broker checks a **token fingerprint
   stored in Postgres** (D1, §5), not an HTTP call to device-gateway. There is no new runtime
   dependency, revocation is just data, and the broker holds no signing key. The rollout is gated
   on an audit that every active device's fingerprint is recorded and matches.
3. **Hygiene and detection are split off (Phases 2–3).** That way they can't hold the critical
   fix back.
4. **A process fix (Phase 3).** Every auth boundary gets a negative test (§1).

---

## 1. Why this was missed

This is a process gap, not a single bad commit. Each step below was reasonable on its own, and
together they kept the hole invisible for five months.

1. **It was there from day one.** The JWT authenticator and `acl.conf` arrived in the first
   `poc` commit (`d3b4372`, 2026-05-20). Nobody ever designed the broker's auth. It was
   inherited.
2. **Every later change preserved it on purpose.** The backend teardown (2026-06-16) ported
   provisioning with _"JWT claim shapes preserved byte-identical for EMQX"_. That was the right
   call for not breaking the fleet, but it turned an unreviewed POC config into a contract to
   protect rather than a design to audit. The comment
   `// EMQX ACL keys off clientid` in `provisioning.service.ts` recorded the **intent** as if it
   were **fact**.
3. **The ACL file looks correct.** `users/${username}/devices/${clientid}/…` reads as per-device
   isolation. The flaw is not in that file at all. It is in what fills the placeholders: values
   the **client** chooses, which nothing ties to the token. Reviewing the ACL file, which is
   what everyone did, can't find it.
4. **We only ever tested that things connect, never that things are refused.** There are zero
   negative MQTT tests in `tests/` (no `0x87`, no "not authorized"). The only broker sanity test
   asserts that a credential **is accepted**. A boundary nobody tries to cross always looks
   intact.
5. **One shared `JWT_SECRET` made everything "just work".** Every service and the broker
   verify with the same key, so any token anywhere was valid everywhere. Nothing ever failed,
   so nothing ever prompted a look.
6. **The threat model changed underneath it, and nothing re-checked the broker.** While the
   only accounts were ours, "any signed token" meant "us". Open Google signup and self-service
   registration (F15.8) turned it into "anyone". No item checks "what does a stranger with an
   account now reach?" when signup opens.
7. **It was found by an audit, and the audit's urgency got lost.** F25.7 found it on
   2026-09-17. The plan then waited on a decision for 39 days behind feature work, because it
   was filed as one row in a 13-row hardening group rather than flagged as an open critical.

**Process changes this item lands (Phase 3):**

- `docs/TESTING.md` gets a rule: every authentication or authorization boundary ships with a
  **negative** test (wrong identity, wrong purpose, wrong owner) beside its positive one.
- A critical finding gets its own containment step and a roadmap "current position" entry the
  day it is found. It doesn't wait behind the full fix.

## 2. Findings

All verified against the code on 2026-10-26. **Repro** items are confirmed on paper only. The
Phase 1 experiments reproduce them.

### A1 — Token and identity are not bound (critical)

- All three broker configs (`oci-k3s-gitops/k8s/base/emqx/resources.yaml`, `compose.yaml`,
  `compose.test.yaml`) use `mechanism=jwt`, `algorithm=hmac-based`, `verify_claims = ""`. EMQX
  checks the signature and `exp`, and nothing else.
- Firmware CONNECT sends `username=userId`, `clientid=deviceId` (`ESP32Code/src/services/mqtt.h`).
  The token carries `{userid, clientid}` (`provisioning.service.ts` `generatePermanentToken`),
  and nothing compares the two.
- This gives one hop to "command another device". Forged telemetry feeds `rules.evaluate`, so
  automation-worker sends **real** commands to the victim's other devices. Forged acks make
  digest record state that never happened.

### A2 — Any token signed with `JWT_SECRET` is an MQTT credential (critical, open signup)

`JWT_SECRET` is shared by api, device-gateway, google-home, socket-server, ota-manager **and
EMQX**. The broker doesn't check `purpose`, so all of these connect:

- `app_usage`: any user, including a brand-new free signup (`localStorage.access_token`)
- `google_cloud_to_cloud_login`: Google holds these
- `device_provisioning`: 1 hour
- `device_usage_refresh`: 10 years

The reverse also holds: **the EMQX pod holds the key that signs admin web sessions.**

### A3 — Wildcard injection through placeholders (repro)

`username=+`, `clientid=+` may render `users/+/devices/+/+/command/#`, which would let one
connection read every command in the fleet. A `/` in the client id could shift topic levels.

### A4 — Any client can take over a session by client id (repro)

mqtt-service connects with the fixed client id `mqtt-service` (`MQTT_CLIENT_ID`). Any accepted
client sending that client id kicks the backend off, so ingestion stops and the two clients
flap. The same works against any device: it goes offline, its LWT fires, and the attacker
receives its commands.

### A5 — No revocation; ownership transfer doesn't revoke

- `device_usage` lives 1 year, refresh lives 10. Firmware refreshes only 7.5 min before expiry
  (`JWT_REFRESH_POLICY`).
- `refreshMqttToken` re-mints after a signature check only, with no DB lookup.
- Re-provisioning upserts `user_devices` by `mac_id`, **keeping the `id`**.
- digest resolves telemetry, acks and heartbeats by `deviceId` alone.

So a device's **previous owner** keeps publishing into the new owner's state indefinitely, and
deleting a device doesn't stop its credential.

### A6 — The backend superuser is accepted on the public listener

The postgres authenticator (`mqtt_user`, `is_superuser=true`) applies to every listener,
including public 8883. In the cluster, mqtt-service only uses internal 1883.
`MQTT_APP_PASSWORD` is therefore guessable online, at one bcrypt per attempt on the single
node's CPU. The cluster also reuses it as the **dashboard password**.

### A7 — ACL file hygiene

- `subscribe …/devices/#/+/status` and `…/devices/#/+/telemetry/#` put `#` mid-filter, so they
  are dead. Their intent (reading siblings' data) is what F25.7 forbids. **Delete.**
- `subscribe …/${clientid}/+/telemetry/#`: nothing subscribes to its own telemetry. **Delete.**
- `subscribe ota/updates/#`: the broadcast is gone everywhere (F3.15). **Delete.**
- Retain is unrestricted. A retained ack or telemetry message replays into digest on every
  mqtt-service resubscribe. Allow retain on `status` only.
- There are two copies (root `acl.conf`, `oci-k3s-gitops/k8s/base/emqx/acl.conf`), whose rule
  order already differs and whose drift nothing checks.

### A8 — Unused listeners (low)

`ws:8083` is still on in every config, and `wss:8084` is still on in the cluster. Nothing uses
MQTT over WebSocket. Neither is routed publicly.

### A9 — The EMQX DB role reaches beyond `mqtt_user` (low)

`prisma/seed.ts` runs `ALTER DEFAULT PRIVILEGES … GRANT SELECT ON TABLES TO <emqx role>`, which
grants SELECT on every future table.

### Already correct — keep

`no_match = deny` + trailing `{deny, all}`; `$SYS/#` denied; `command/#` subscribe-only for
devices; a requested wildcard can't widen a rule's literal level; TLS on the only public
listener; superuser password in the DB only.

## 3. What "done" means

For a device credential issued to device `K` owned by user `U`:

1. CONNECT succeeds **only** with `username=U`, `clientid=K`, and only while `user_devices` row
   `K` exists and is owned by `U`.
2. Tokens of any other purpose are refused.
3. Publish only on `users/U/devices/K/<v>/{status, telemetry/<a>, ack/<a>, heartbeat}`; retain
   only on `status`.
4. Subscribe only on `users/U/devices/K/<v>/command/#`.
5. The superuser credential is refused on 8883.

**Out of scope:** a compromised device lying on its **own** topics (F25.5/F25.8); connection and
throughput limits (F25.10); client certificates (F25.8); `JWT_SECRET` still shared across the
HTTP services (F25.12). This item only removes it from the broker.

## 4. Phase 0 — Containment: `verify_claims` on `purpose` (target: same week)

**What:** add `verify_claims = {purpose = "device_usage"}` to the JWT authenticator in all
three configs. Nothing else changes.

**Why it's safe for the fleet.** The September plan rejected `verify_claims`, and that
rejection still stands for **binding** `userid`/`clientid`: the token carries JSON integers,
EMQX renders placeholders to binaries, and strict equality never matches. A **literal string**
compared to a **string claim** doesn't have that problem. Every token ever issued carries
`purpose` as a string: `@lattice/jwt` `generateToken` spreads it in, and so did the pre-June
backend signer (`701d2f5`, `backend/services/jwt.service.ts`). Every device holds a
`device_usage` token.

**What it closes:** A2 for every non-device token, which means the zero-effort path (free
signup → backoffice token → any device). Google-held tokens and a token exfiltrated from a
browser stop working on the broker.

**What it does NOT close:** a free account can still script the provisioning flow (device-sim
does exactly this against the real API) and obtain a genuine `device_usage` token, and A1
still applies to that token. Phase 0 raises the bar from "copy a string" to "run a script". It
is a speed bump, not the fix. **Phase 1 follows immediately.**

**Steps:**

1. **E0 (test stack):** confirm the 5.6 env form
   (`EMQX_AUTHENTICATION__1__VERIFY_CLAIMS__PURPOSE=device_usage`, or the list form if the map
   form is rejected; check with `emqx ctl conf show authentication`). Then confirm:
   - an `app_usage` token is refused (this is the repro, before and after);
   - a provisioned sim device still connects;
   - mqtt-service (postgres path) is unaffected.

   **E0 result (2026-10-26, test stack, EMQX 5.6.0):**
   - _Before:_ a login (`app_usage`) token as the password with `username=1`, `clientid=21`
     connects on 11883 **and** 18883 (TLS), gets SUBACK QoS 1 on
     `users/1/devices/21/+/command/#`, and receives a superuser-published command. Controls: a
     token signed with the wrong secret and a truncated token are refused `135`.
   - **The map env form does NOT work and fails silently.**
     `EMQX_AUTHENTICATION__1__VERIFY_CLAIMS__PURPOSE=device_usage` boots cleanly, but
     `conf show` still says `verify_claims = ""`, and the attack is still accepted.
   - **The working form is the HOCON literal:**
     `EMQX_AUTHENTICATION__1__VERIFY_CLAIMS={purpose = "device_usage"}`. `conf show` then reads
     `verify_claims {purpose = device_usage}`. The attack is refused on both listeners. A genuine
     `device_usage` token still connects, subscribes and receives. mqtt-service and the sims
     reconnect.
   - **The refusal code differs:** a claim mismatch returns `134` (bad username or password), a bad
     signature `135` (not authorized). Tests must accept either as "refused".
   - `conf show` also reveals `acl_claim_name = acl` (default): the JWT authenticator would honor
     ACL rules embedded **in** a token. We issue none, but any holder of `JWT_SECRET` could mint
     one. This is one more reason the broker must lose `JWT_SECRET` (Phase 1 removes the
     authenticator).

2. `compose.yaml` and `compose.test.yaml`. The full e2e run shows the same **set** of failures
   as before (`reference_e2e_suite_traps`).
3. **Staging:** an `k8s/overlays/staging` patch on the emqx env, **not** base. `base/emqx`
   feeds both overlays, and Argo CD auto-syncs. Verify that real staging devices reconnect and
   that the EMQX client count recovers.

   **Done 2026-10-26** (`oci-k3s-gitops` `abc9be1`). Argo CD synced after ~3 min, and emqx-0 rolled.
   `conf show` on staging reads `verify_claims {purpose = device_usage}`. mqtt-service reconnected
   (7 retries during the roll). No staging device was connected before or after (0 on ssl; 3
   devices, 2 active, all offline), so "devices reconnect" had nothing to observe. **C5 is
   unproven on real staging:** no staging test credentials exist on the dev machine or in CI.

4. **Prod:** move the patch into base and delete the staging copy, in one commit. Watch the
   client count against online devices, and confirm `LatticeMqttNoConnections` stays quiet.

   **Done 2026-10-26** (`oci-k3s-gitops` `c8c1a76`, pushed 08:25:25Z). Both Argo CD apps synced at
   +210 s, and prod emqx-0 was recreated at 08:29:22Z. `conf show` reads
   `verify_claims {purpose = device_usage}` in both `lattice-prod` and `lattice-stg`. The only prod
   board (client `6`, user `1`) reconnected with its stored token: `online=t`, `last_online_date`
   08:29:36. That's the real-hardware proof that fleet tokens carry `purpose`. mqtt-service is
   back, and the only active alert is `Watchdog`. C5 itself has no prod or staging run (no
   credentials); it rests on the identical config proven locally.

5. **Side check:** confirm the prod `JWT_SECRET` is not the dev placeholder
   (`your_jwt_secret_key`). Compare lengths or hashes, and never print the value.

   **Result (2026-10-26):** staging (len 38) and prod (len 46) each differ from the placeholder,
   from `.env` and from `.env.test`, and from each other. The control (`.env.test` vs itself)
   matched. **Side finding, outside F25.7:** the local `.env` **is** the placeholder (len 19,
   same hash), and `frpc.toml` publishes the local dev api / gateway / socket / ota and emqx 1883
   via `lattice-local.duckdns.org` whenever the `tunnel` profile is up. Anyone who knows the
   placeholder can forge an admin token for the local stack. Raised with the user; not changed.

**Rollback:** revert the one commit. Tokens never changed, so devices reconnect on their next
retry.

## 5. Phase 1 — Binding + revocation: D1, token fingerprint in Postgres

**D1 (decided by the user 2026-10-26):** the broker authenticates a device by looking up a
SHA-256 fingerprint of that device's current token in Postgres, using EMQX's built-in
`password_based` / `postgresql` authenticator. That's the same mechanism it already uses for
`mqtt_user`, against the same database. The JWT authenticator is removed, and so is the broker's
`JWT_SECRET`.

### 5.1 Data

- **New table `device_mqtt_credentials`** (migration + `prisma/SCHEMA.md`):
  - `user_device_id` is the PK, a FK to `user_devices.id` with `ON DELETE CASCADE`.
  - `token_sha256 CHAR(64)` holds the current token; `prev_token_sha256 CHAR(64) NULL` holds the
    one before it.
  - `updated_at` records the last write; `last_seen_match_at` records the last time the device
    presented the current token over HTTP (used by the audit gate).
- **New view `mqtt_device_auth`** (`user_devices` ⋈ `device_mqtt_credentials`). It exposes only
  `id`, `user_id`, `token_sha256`, `prev_token_sha256`. Ownership is read **live** from
  `user_devices`, never copied, so a transfer can't drift.
- **EMQX role grants:** `SELECT` on `mqtt_user` and on the view **only**. Revoke everything else,
  including the default-privileges grant (A9 moves into this phase, because the grants change
  anyway). `prisma/seed.ts` runs in the migrate image and is prod-facing, so the brief for this
  step must show the exact SQL.

### 5.2 Who writes fingerprints (device-gateway)

All writes go in one service module, `services/mqtt-credential.service.ts`.

| Moment                                       | Write                                                                                                                                                                                                                                                                      |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Provisioning (`provision`)                   | upsert with `token_sha256 = sha256(new token)`, `prev = NULL`. A re-provision to a new owner therefore kills the old owner's token immediately (A5).                                                                                                                       |
| Refresh (`refreshMqttToken`)                 | First check that the row exists and is owned by `claims.userId` (R1, otherwise 401 and no token). Then `prev ← current`, `current ← sha256(new token)`.                                                                                                                    |
| Config fetch (`GET /config`, `device_usage`) | **Backfill only**: if there's no credential row, and `claims.clientid == deviceId` and `claims.userid == row.user_id`, insert the fingerprint of the presented token. Never overwrite an existing one. If the presented token matches `current`, set `last_seen_match_at`. |

The backfill-only rule is permanent. It lets a device that was offline for the whole rollout
self-heal at its next boot. Firmware fetches config at boot even if MQTT failed
(`main.cpp` setup path). It can't be abused to re-register an old token, because once a row
exists it's never overwritten from this path.

### 5.3 Broker

**Authenticator chains** (per listener; E5a confirms this works in 5.6):

| Listener                      | Chain                                   |
| ----------------------------- | --------------------------------------- |
| `ssl:default` 8883 (public)   | `device-postgres` only                  |
| `tcp:default` 1883 (internal) | `device-postgres`, `mqtt_user-postgres` |

`device-postgres` query, preferred form (E6 confirms that `${password}` is usable inside SQL):

```sql
SELECT token_sha256 AS password_hash FROM mqtt_device_auth
WHERE id::text = ${clientid} AND user_id::text = ${username}
  AND encode(sha256(convert_to(${password}, 'UTF8')), 'hex') IN (token_sha256, prev_token_sha256)
```

…returning the matched hash, with `password_hash_algorithm {name = sha256, salt_position = disable}`.

- A non-matching token returns **no row**, which means `ignore`. On 8883 the chain then ends,
  so the client is refused. On 1883 the chain falls through to `mqtt_user`, which also finds no
  row, so it's refused too.
- `+`, `/`, and `mqtt-service` as a client id are bound as query parameters, so they match no
  row (A3, A4).
- The superuser has no row in the view, so it's refused on 8883 (A6).

**If E6 fails** (no `${password}` in SQL): use the simple form,
`SELECT token_sha256 AS password_hash … WHERE id::text = ${clientid} AND user_id::text = ${username}`.
That form accepts only the **current** token. A refresh whose response is lost then locks the
device out on its next reconnect. It recovers only if it refreshes again while still connected
(it keeps retrying near expiry) or at its next boot. This happens at most once a year per
device. Record it as an accepted trade (§9).

**E7 matters for the chain:** when a row is found but the password doesn't match, EMQX returns
`deny`, not `ignore`. The preferred query never returns a mismatched row. The fallback query
does, which is fine, because deny is the right answer there.

### 5.4 What this closes

| Finding | How                                                                               |
| ------- | --------------------------------------------------------------------------------- |
| A1      | identity = (clientid, username) row **and** that row's fingerprint                |
| A2      | only `device_usage` tokens are ever fingerprinted; the broker has no `JWT_SECRET` |
| A3, A4  | parameter-bound lookup; no row for `+` or `mqtt-service`                          |
| A5      | delete cascades the credential row; transfer resets it; refresh checks ownership  |
| A6      | 8883 chain has no `mqtt_user`                                                     |
| A9      | grants narrowed to the view + `mqtt_user`                                         |

### 5.5 Rejected alternatives (kept so they aren't proposed again)

- **HTTP authenticator in device-gateway (the 2026-09-17 D1).** It works, and it could have been
  shadowed safely. It was rejected for adding a runtime dependency (gateway down = no device can
  connect), a new internal port, and an HTTP call on every connect.
- **`verify_claims` binding of `userid`/`clientid`.** It can't match: EMQX uses strict equality,
  placeholders render as binaries, and tokens carry JSON integers. Making it work needs reissued
  tokens, a firmware change and a fleet OTA, and it still gives no revocation.
- **Reissued tokens with an `acl` claim / a separate device key.** Same firmware + OTA cost; no
  revocation.

A6 then falls back to a long random `MQTT_APP_PASSWORD` plus F25.10, recorded as a trade.

### 5.7 Rollout: record first, audit, then flip

The broker keeps deciding with JWT + the Phase 0 `purpose` check until the audit passes. Writing
fingerprints changes no connect behaviour, so steps 1–4 below are risk-free for devices.

1. **Failing tests** (§8) on a fresh ephemeral stack.
2. **Schema:** table + view + grants (migration, SCHEMA.md, seed grants).
3. **Gateway writes** (§5.2) + unit tests for every branch: provision, transfer, refresh ok,
   refresh on a deleted or transferred row, backfill insert, backfill refusal on a claim
   mismatch, no-overwrite, match stamp.
4. **Local flip:** both compose files swap the JWT authenticator for `device-postgres`, and
   `JWT_SECRET` is removed from the emqx services. The §8 matrix passes, and the e2e failure
   **set** is unchanged.
5. **Staging, record phase:** migration + gateway image via Kargo, with the broker unchanged.
   Restart every online staging device (existing lifecycle `restart` command), so each one
   fetches config and gets backfilled.
6. **Audit gate** (run as a read-only query, shown to the user):
   - every device online in the last 30 days has a credential row;
   - each such row has `last_seen_match_at` after the restart;
   - list every exception by id.

   **Flip only at zero exceptions**, or with each exception explicitly accepted by the user.

7. **Staging flip** (overlay patch) + staging subset of §8 with `TEST_TARGET=staging` + invert the
   sanity test into C10.
8. **Prod:** promote the migrate + gateway images manually, restart online devices, audit gate,
   then flip in base (one commit).

**Rollback:** revert the flip commit. The broker goes back to JWT + `purpose`, and since no token
was ever reissued, every device reconnects on its next retry. The table and the gateway writes
are harmless to leave in place.

**Residual lockout path, and why the gate covers it:** a device with no matching fingerprint
whose MQTT drops **without a reboot** doesn't re-fetch config (firmware only fetches config while
MQTT is up, after boot). It stays out until it's power-cycled. The audit gate exists to make
that set empty before the flip. A device offline through the whole rollout self-heals at its next
boot (§5.2 backfill).

## 7. Phase 3 — Detection + guardrails

- **Alerts** in `k8s/base/monitoring/lattice-alerts.yaml`, using the E5e names. A healthy fleet
  has an authz-deny rate of **exactly zero**, so alert `critical` if it stays above zero for
  30 min. Add an authn-failure alert on the EMQX counter for 8883 (sustained failures = a locked-out
  device or a probe). Both fit the failures-only policy.
- **`docs/TESTING.md`:** the negative-test rule from §1.
- **Docs:** `docs/ARCHITECTURE.md` (the device auth path); the F25.7 roadmap row, a
  session-log entry and the "current position" header; `oci-k3s-gitops/CLAUDE.md` (the note that
  `base/emqx` deploys to both environments).
- No firmware change, so the parity rule doesn't apply.

## 8. Test matrix (`tests/e2e/mqtt-acl.e2e.test.ts`)

**Fixtures:** D1 is device `K1` of user `U1`. D3 is `K3`, also owned by `U1`. D2 is `K2`, owned
by `U2`. All are provisioned through the real flow.

**How refusals are detected:** an **MQTT v5** client gets reason code `0x87` on a refused
SUBSCRIBE or QoS 1 PUBLISH. For QoS 0, a superuser observer on `#` watches, after a
positive-control publish.

## 9. Accepted trades

- **An already-connected revoked device stays connected** until it disconnects; an operator
  kicks it from the dashboard (tailnet only). EMQX 5.6 API keys are full-admin with no scopes,
  so handing one to a service would be a bigger hole than this gap.
- **digest keeps trusting the topic's `userId`** for socket emits. Once C9 holds, the broker has
  already bound the username to the current owner.
- **`device_usage` still lives 1 year on the HTTP routes** (camera, config, OTA download), which
  check purpose but not the row. These fold into F25.8.
- **No "revoke but keep the device" action.** Revocation happens through delete or
  re-provision, which are the only flows that exist today. Clearing a fingerprint by hand would
  be undone by the backfill at the device's next boot, so a true revoke needs a `revoked_at`
  column. Add it when a UI needs it.
- **If E6 forces the fallback query:** a refresh whose response is lost can lock a device out on
  its next reconnect until it refreshes again or reboots (§5.3). This happens at most once a
  year per device.
- **The broker now reads app data** (one view). The view exposes ids and fingerprints only;
  SHA-256 of a high-entropy JWT can't be reversed into a usable token.
